# Media notes

These are the rules behind `flora_deploy.media` (`index.py`, `cuts.py`, `rangedecode.py`,
`sources/`). They were found empirically with PyAV 16.0.1 (bundled FFmpeg, libx264, SVT-AV1,
libaom, libx265, libdav1d) and checked against NVIDIA's `batch_utils.media` at the pinned Flora-TempSeg
revision (`78a0e4ac`). The checks are in `tests/nvlink/test_media_parity.py` and
`tests/nvlink/test_media_adversarial.py` (edit lists, intra refresh, mid-GOP starts, `.mov`,
low timescales, HEVC, many-episode SVT-AV1); the fixtures are
generated by `flora_deploy.media.synth` when the tests run.

## Containers

Only MP4/MOV inputs are supported (`.mp4`, `.mov`, `.m4v`): the decoder opens every dataset
file through `media.avsafe.open_input`, which restricts FFmpeg to the `mov` demuxer, local files
and no external data references. Inside MP4 the codec is free (H.264, HEVC, AV1, MPEG-4 Part 2,
fragmented MP4 included). Any other container, such as Matroska (`.mkv`) or WebM (`.webm`), is
refused with:

```
unsupported container (only MP4/MOV): <path>
```

Convert such a file to MP4 first, e.g. `ffmpeg -i in.mkv -map 0:v:0 -c:v libx264 out.mp4`.

## Reference cut

The oracle input for an episode is **our** stream-copy cut (`cuts.stream_copy_cut`). It is a
PyAV remux of exactly the episode's packets, in decode order:

- the source `time_base` is requested. movenc keeps it only for timescales ≥ 10000; below that
  it doubles the timescale until it reaches 10000 (a 1/30 track becomes 1/15360 in the cut,
  fixture `timescale_30`). Every rational (`pts_us`, rate) is unchanged, so this is harmless,
  but `StreamIndex.time_base` is the *source* time base, not necessarily the cut's;
- pts and dts are shifted so the first presented frame has `pts = 0`;
- packet `duration`s are copied;
- codec parameters come from `add_stream_from_template`;
- the output is MP4 with the video stream only;
- it is written to a temporary name and renamed when complete, so a failed cut leaves no file.

Only **oracle-eligible** ranges are cut (next section). For any other range, `stream_copy_cut`
raises `NotKeyframeAligned` and its `.reasons` lists why.

Probe values are container properties, so "what a cut reports" only means something once the
cut procedure is fixed. A different tool (for example `ffmpeg -ss/-to -c copy`) may choose other
packets or edit lists. Use this one.

## `average_rate` (the key rule)

- **The mov demuxer computes `avg_frame_rate = av_reduce(timescale × n_samples, Σ stts, INT_MAX)`
  over the file it opens.** The MP4 muxer writes each stts entry as the dts delta to the next
  sample, and the last entry as that packet's `duration`. Those values are exactly the
  `duration`s the source demuxer reports for the same packets. So:
  **`rate_cut = av_reduce(timescale × n, Σ duration of the episode's packets)`**. It is computed
  from the source packets without writing a cut. Doubling the timescale below 10000 (movenc)
  doesn't change the ratio.
- The concatenated file's `stream.average_rate` is the same formula **over all episodes**, so it
  often differs from the per-episode rate. Evidence from the fixtures (whole-file rate → cut rate):

  | Fixture | Whole file | Episode cuts |
  |---|---|---|
  | `mixed_rate` | 325/14 | 30, 15, 25 |
  | VFR | 1875/62 | 24000/767, 18600/631 |
  | `tail_cat` | 1800/61 | 1200/41, 30 |

  CFR files with uniform durations give 30 for both.
- **Episode joins change the last stts.** The concat demuxer offsets each file by its stream
  duration, so the boundary dts delta becomes the previous file's "duration remainder", not the
  frame interval.
  - With x264 B-frame pyramids, a per-episode file can report a duration 10 ticks short (8694
    instead of 8704 at 1/15360). That gives a boundary delta of 502.
  - The cut of that camera's episode then reports `43520/1449` instead of 30. NVIDIA rejects the
    3-view sync (`media.py:63-65`), and so does our envelope.
  - Seen in `test_lerobot_v3_source_episodes_match_probe_and_nvidia_inputs[kw0]`. With
    `bframes=0`, or with SVT-AV1 (LeRobot's default), every cut is exactly 30.
- **No last-sample correction.** A 120-frame file whose last stts is 20× normal reports
  `3600/139`, which is the raw formula. FFmpeg's old ">100 samples, abnormal last duration"
  heuristic does not apply in this build.

## PTS, duration and CFR

- `pts_us` is in presentation order (ascending pts), relative to the first presented frame, as an
  exact `Fraction` µs.
- Tail: `frame.duration` of the last presented frame is the duration of the packet that carried it,
  which is the source packet with the largest pts. With B-frames this is **not** the last packet
  in decode order: in `tail_x3`, the modified last-decoded packet doesn't change `duration_us`.
- `duration_us = round(last + tail)`. Python rounds a `Fraction` with banker's rounding, matching
  `media.py:52`.
- CFR is NVIDIA's test against `i·1e6/rate` within 1 µs. A non-standard tail breaks CFR even when
  the frame spacing is uniform, because the rate shifts. VFR sources are indexed exactly; they come
  out `cfr=False`, and the 3-view and single-view-robot-caption paths then reject them.
- `index_stream(decode=True)` decodes the cut's packets with a fresh decoder (what `probe` does on
  the cut) and reads PTS, in decoder output order, and the tail from the output. A decoder
  exception becomes the `decode_error` ineligibility reason and output that differs from the
  packet prediction becomes `decoder_mismatch`, so corrupt packets and broken reordering are
  caught. The packet-mode envelope cannot see either. Use `index_episode(decode=True)` for oracle
  candidates. Both modes equal `probe(cut)` on every eligible fixture.

## Episode ranges and oracle eligibility

- LeRobot v3 `from_timestamp`/`to_timestamp` are float sums of per-episode
  `get_video_duration_in_s`. Frames are assigned when `start − h ≤ t < end − h`, where `h` is half
  the file's median packet duration.
  - Selection uses integer bounds in time-base units (`pts ≥ ⌈(start − h)/tb⌉`,
    `pts < ⌈(end − h)/tb⌉`) and a bisection over the file's sorted pts.
  - The cost is O(log N + k) per episode, plus one O(N log N) sort per file.
- **The metadata is not trusted.** `sources.verify_episode` checks each camera's
  `(file, from, to)` against the file's sample table and raises `SourceError` in these cases:
  - the file is missing;
  - the range ends after the file, or selects no frame (the `aloha_mobile_wipe_wine` ep 43 case:
    the range starts where file-000 ends, and the frames are in file-001);
  - the range's frame count differs from LeRobot's `length`.
- **The governing rule:** an episode is oracle-eligible only when the stream-copy cut is
  guaranteed to decode to the source's frames. `plan_episode` decides this, and the index, the
  cut and range decode all share its result. Anything else fails closed with
  `StreamIndex.ineligible` reasons (`starts_on_keyframe=False`, `EpisodeIndex.ineligibility`):

  | Reason | Condition |
  |---|---|
  | `not_keyframe` | the first packet in decode order is not a sync sample |
  | `not_random_access` | it is a sync sample but not a true random-access point (below) |
  | `leading_pictures` | a packet of the range presents before the first one (open GOP) |
  | `non_contiguous` | other packets sit between the range's packets in decode order (a B-frame GOP split mid-pyramid) |
  | `edit_list` | a packet in the cut's span is flagged `AV_PKT_FLAG_DISCARD` |
  | `decode_error`, `decoder_mismatch` | `decode=True` only (above) |

- **Random-access points** are checked by inspecting the bitstream of every sync sample during
  the scan:
  - **H.264:** an IDR slice (NAL 5) comes before any non-IDR slice. x264 `intra-refresh` and
    open-GOP recovery points set `stss` on non-IDR frames. A cut started there decodes 0.2 s late
    (39 of 45 frames), so those ranges are `not_random_access`.
  - **HEVC:** the first VCL NAL is an IRAP (16–21). CRA/BLA leading pictures are caught by
    `leading_pictures`.
  - **AV1:** the temporal unit's first frame header is a shown `KEY_FRAME`. `show_existing_frame`
    (including the display of a forward key frame), hidden key frames and intra-only frames are
    rejected.
  - **Other codecs:** a decode cross-check. Decoding the first GOP from the cut start must output
    every packet's frame, with pixels equal to decoding from the previous keyframe.
  - Every sync sample of the x264, SVT-AV1 and libx265 fixtures, and of the many-episode SVT-AV1
    `g=2` file, passes.
- **Edit lists.** The mov demuxer applies an edit list by flagging trimmed samples
  `AV_PKT_FLAG_DISCARD`. libavcodec decodes those samples but never outputs them. Two cases
  produce such samples:
  - `ffmpeg -ss … -c copy` pre-roll;
  - a zero-duration last sample, where movenc ends the edit list before it.

  A remux drops the flag and would make the trimmed frames visible, so these ranges are
  `edit_list`. The index excludes discarded packets: it describes what the source shows (the
  `probe` of the original file, and `decode_selected` of it, in fixtures `edit_trim` and
  `edit_last0`).
  - Exception: `probe(original)`'s `rate` for `edit_last0` counts the hidden sample's zero stts
    (400/13), while ours does not (30). The episode is ineligible, so no oracle compares this.
  - Edit lists that only shift time (B-frame delay, `-output_ts_offset`) produce no discards.
    Those stay eligible.
- **What the index describes for ineligible ranges:** the frames the source decoder outputs
  for the range.
  - Discarded packets are excluded.
  - Non-contiguous ranges count only the selected frames, never the neighbours inside the
    decode span.
  - When the file has no random-access point at or before the range (a whole file that starts
    mid-GOP, after an RTSP/NVR segment split), the decoder's actual output is measured. h264
    drops frames until the first IDR, so a file of 80 packets is 60 frames, as `probe` of the
    original file reports.
- x264 inserts scene-cut keyframes. A "single-GOP" or intra-refresh fixture needs `scenecut=0`.
- `synth.concat_like_lerobot` fails with `EINVAL` on x264 B-frame episodes of different
  lengths/GOPs (the concat demuxer's dts become non-monotonic). The same is probably true of
  LeRobot with `vcodec=h264`, so B-frame concatenation fixtures use equal reorder delays.

## Decoding and colour branches

- `rangedecode.iter_frames` / `decode_selected` decode from the source, with the scan reused
  (`scan=` or `scans=`):
  - **Eligible ranges:** a fresh decoder (`err_detect=explode`, `thread_count=1`) is fed exactly
    the cut's packets and then drained. Every output frame must be the next indexed frame (no
    filtering). The output is bit-identical to NVIDIA `decode_selected` on the cut for H.264
    (with B-frames), HEVC, SVT-AV1 and libaom AV1 decoded by libdav1d, and for VFR, `.mov`,
    timescale-30 and many-episode inputs.
  - **Ineligible ranges:** decoding starts at the previous random-access point (or at the file
    start), and the output is filtered to the indexed frames by absolute pts. The result equals
    the source decoded from its start (fixtures: edit list, intra refresh, mid-GOP start,
    non-contiguous).
  - **Timestamp guard:** every returned frame's **absolute** source pts must equal
    `StreamIndex.source_pts[i]`, and its relative PTS must equal `pts_us[i]`. NVIDIA's guard is
    relative to the first decoded frame, so a decoder that dropped leading frames passed it and
    returned frames shifted by N. Ours raises `MediaError`.
- Seeking uses the start packet's **pts**. The mov demuxer seeks by presentation time; seeking by
  dts landed one GOP early with B-frames, and a test checks that it lands exactly. If a seek
  overshoots, the code falls back to demuxing from the file start.
- Scans are parallel numpy arrays, about 50 B per packet (the old per-packet objects took about
  335 B). `index.ScanCache` is an LRU bounded by retained bytes (256 MiB by default). Episodes
  of a concatenated file are indexed consecutively, so each file is demuxed once without holding
  a whole dataset.
  - Micro-benchmark (`test_benchmark_100k_packets_500_episodes`): 100k packets and 500 episodes
    index in about 0.4 s in total (0.8 ms per episode). The old selection alone took about
    170 ms per episode, roughly 85 s in total.
- Source selection: attached cover-art streams are ignored. A file with more than one real
  video stream raises `MediaError`, because which camera to use is ambiguous.
- Branch (`media.py:85`): canonical RGB is used only when `canonical` (3-view) is set and the frame
  is `yuv420p`, `width % 16 == 0`, `height % 2 == 0`, colorspace ∈ {2, 5, 6} and range ∈ {0, 1}.
  Everything else goes to `to_image().convert("RGB")`.
  - Fixtures cover both branches: BT.709-tagged, full-range (`yuvj420p`, which fails the format
    test) and width 72.
  - SVT-AV1 tags `color_range=1`, which is still canonical.
- Colour tags are **not** preserved byte for byte. A `.mov` source with an `nclc` colr box (which
  has no range field) decodes with `color_range=0`. movenc writes `nclx` with `full_range=0`, so
  the MP4 cut decodes with `color_range=1`.
  - Both values are in {0, 1}, so the branch and the pixels are unchanged. Fixture `mov_nclc`
    (BT.470BG, canonical-eligible) is bit-exact on both branches.
  - `StreamIndex.colorspace/color_range` are codec-parameter tags and **advisory**. NVIDIA picks
    the branch per decoded frame (`media.py:85`), so never pre-select it from the index.
- `canonical_rgb` is **injected** (`decode_selected(..., canonical_rgb=fn)`). Linked mode passes
  NVIDIA's `vendor/support/canonical_rgb.py`; nothing NVIDIA-licensed ships here. If a frame is
  eligible and no function was given, the call raises.

## Envelope

`index.stream_checks` and `envelope_checks` collect every NVIDIA check instead of raising, with
file:line citations in the docstrings:

- size: 0 < size ≤ 256 MiB. The check accepts when the upper estimate fits (payload + 4 KiB +
  32 B per sample) and rejects when the payload plus minimal boxes does not. In the window
  between, the cut is made in a temporary directory and measured (eligible ranges only), so there
  is no false reject just under the cap;
- streams: exactly one video stream;
- rate ≥ 4;
- frame size: 1..4096 px;
- PTS: present and strictly increasing;
- length: t < 120 s, ≤ 7200 frames, ≥ 2 frames, duration ≤ 120 s;
- cameras: roles must be `main` or `main/left_wrist/right_wrist`;
- 3-view: views in sync, and CFR;
- profile: valid profile, human single-view only, yam32 rules, instruction ≤ 2000 characters;
- single-view robot captioning needs CFR.

The verdict agrees with NVIDIA's `DataEnginePipeline._inputs` on cuts of every fixture, including
boundary cases such as fps 3/4, 7200/7201 frames, 120/121 s, 4112 px wide, de-synced 3-view and
VFR 3-view.
